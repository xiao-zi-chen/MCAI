# AGX 起床战争赛项设计草案

状态：2026-10-20 的本地设计与试验工作。本文的新赛项接口尚未在 AGX 上线；Minecraft 经典规则、实时观战及本地整局回放已实现，投稿策略驱动器及平台回放接入尚待联调。

## 1. 已核对的现有平台

- [AGX](https://agx.cool/) 的公开介绍要求选手在本地开发 JavaScript 策略，再上传代码参加比赛。
- [公开游戏接口](https://agx.cool/api/v1/games?main_only=false) 当前返回 `tank/rsi-tank-3.1` 与 `poker/rsi-poker-4.1`，入口都是 `act(o)`。
- [OpenAPI](https://agx.cool/api/openapi.json) 的 `CreateVersion` 要求 `source` 字符串；其中 `model` 是字符串元数据，不能据此认为平台支持上传神经网络权重。
- `CreateAgent.game_id` 的公开枚举目前只有 `poker`、`tank`。新增赛项需要修改平台注册、校验、调度、执行器和回放，不能只上传 Minecraft 插件。
- 当前坦克公开规则给出源码 4 MiB、JS 堆 128 MiB 等限制。这些是坦克的规则，不能直接当作起床战争的现成预算。
- 本工作区的“奇谋竞技场”是另一个本地项目；目前没有证据表明它就是 AGX 的服务端仓库。

## 2. 首个正式玩法

建议名称：**悬空夺床 / SkyDuel**。底层采用真实 Minecraft Java 1.21，固定 Paper 构建与 Screaming BedWars 0.2.44。

第一版使用 1v1、两队、固定装备/商店、对称悬空岛，保留采集、购买、搭路、护床、拆床、近战、死亡复活与最终淘汰。先验证两个独立投稿之间能完整比赛，再扩到 2v2。

第一版做“策略赛”：选手决定目的地、购买、搭路路线、攻击/撤退时机及拆床目标。平台提供公开且版本固定的底层寻路、合法放置和战斗执行。辅助程序也是规则的一部分，双方完全相同。后续可另开键鼠级“控制赛”，两种控制层级不能混用一个榜单。

本地 v0.4 规则采用 30 分钟上限，最后一支未被最终淘汰的队伍获胜。超时双方仍存活则平局；局部伤害、普通击杀和采集数只作分析，不加权替代胜负，避免反复刷击杀得分。当前已加入 20 分钟统一移床、25 分钟缩圈；正式赛季仍需多局平衡测试。

每组对手至少交换红/蓝出生点各赛一局。多地图时对同一组地图轮换；战力应从多局交叉对战判断。地图种子相同也不保证 Paper、网络及物理线程的执行逐位一致。

## 3. 参赛者到底交什么

**第一阶段提交一个 UTF-8 的 `agent.js`，提供同步 `function act(o)`。**

选手可以自己写规则、搜索/规划算法，也可以本地训练小模型，再导出为纯 JavaScript 推理函数与内嵌数值权重。均通过同一个投稿入口，遵守相同的观察、动作和资源限制。每份源码形成不可变版本，正式比赛使用冻结版本。

不要求选手提交 Minecraft 客户端或拥有运行中的服务器。比赛时由平台运行策略；选手电脑离线不影响比赛。训练由选手在自己的设备完成，平台承担审核和比赛推理。

首版不把 Python、任意 JAR 或 Docker 镜像当成投稿格式。之后如果纯 JS 的模型推理确实成为瓶颈，可以新增“受限 ONNX 模型附件 + JS 控制器”：需要增加附件接口、哈希绑定、算子与形状校验、独立推理进程和资源记账。这是平台扩展计划，当前 AGX 没有已确认的这种能力。

参数量仅作为提交信息，主要限制实际运行成本。相同参数量的循环网络、MLP 和注意力模型可能耗时不同。先对小型 MLP 导出做一致性及沙箱基准，再决定允许的模型规模。

## 4. 观察合同（草案 v0.1）

`act(o)` 每次只接收该席合法观察，下一局重建上下文；普通 JS 全局变量可保存本局记忆。

| 字段 | 内容 |
| --- | --- |
| `v, rulesVersion, tick, phase, seat, team` | 接口版本、规则版本、游戏刻度、阶段与席位 |
| `me` | 自身位置、速度、血量、背包、装备、冷却、是否在商店交互范围内 |
| `allies` | 明确公开给本队的信息；1v1 时为空 |
| `visibleEnemies` | 视距内且通过服务器射线遮挡检查的对手；当前可见标识、位置和外观装备 |
| `map` | 初始静态地图与基地/资源点/商店位置公开；动态方块只提供本席可见的更新 |
| `teams` | 公共床存活、最终淘汰等信息；不含对手背包和后台决策 |
| `events` | 公共事件、自身操作结果、被拒动作的原因 |
| `orderStatus` | 当前任务的进行/完成/失败状态，帮助选手重规划 |

隐藏对手的精确血量、攻击冷却、背包、不可见坐标和藏在床防御内部的方块不能通过观察、寻路器、错误消息或回放实时接口泄漏。最后看见的位置只能由选手自己记住，不能在后台继续更新。

本地 PVP ROBO 模型使用 31 维研究观察，包含对方血量/冷却等特权状态，还用命中次数计分。它可以证明小模型可在本机运行，不能直接当作本赛项的合法全局策略。模型迁移需要依据最终合法观察和起床战争奖励重新训练/微调。

## 5. 动作合同（草案 v0.1）

返回 `{v:1, order:{...}}`，一次更新一个任务，不直接调用服务器命令。允许的命令如下：

| `order.type` | 参数与语义 |
| --- | --- |
| `wait` | 清空持续控制，等待下次决策 |
| `move` | `target:{x,y,z}`；在已知可走地形上移动，不能飞行/传送 |
| `bridge` | `target:{x,y,z}`；按公开规则用背包方块逐格搭路，受放置距离、碰撞与库存限制 |
| `place` | `block:{x,y,z}, item`；在合法位置放置一块已有方块 |
| `mine` | `block:{x,y,z}`；持续破坏一个可见、可达、规则允许的目标，保留工具挖掘时间 |
| `buy` | `item, quantity`；只在自己的商店交互范围内，按统一价格扣资源 |
| `attack` | `targetId`；只针对当前可见敌人，使用公开的瞄准/攻击执行逻辑，遵守冷却、射线和距离 |

重复同一任务应继续执行，不每次清空寻路或挖掘进度。切换任务取消原任务；攻击目标失去可见性后停止追踪，不依靠隐藏的实体坐标继续攻击。底层执行器也只能使用该席已经获准的信息。

目标策略文件样例在 `submission-kit/agent.js`。这是合同示例，当前尚没有把该合同转换成 Minecraft 操作的正式执行器，不能把样例描述为已可上传 AGX 的程序。

## 6. 时序与资源预算

初始候选：Minecraft 20 TPS，策略每 4 tick 决策一次，即每席 5 Hz。若近战/搭路实测需要更高频率，再统一升到 10 Hz 并更新规则。

每个决策刻度先冻结各席观察，所有策略独立执行，行动都安排在同一个后续刻度应用。不能谁先算完谁先执行，也不能阻塞 Minecraft 主线程等待选手代码。

待实测的起始预算：源码 4 MiB、每席堆 128 MiB、栈 1 MiB、初始化 2 秒、单次决策 20 ms、每席整局累计 CPU 30 秒。代码初始化、模型解码与推理都计入预算。5 Hz、10 分钟最多每席 3,000 次回调；两个席位各平均 5 ms 的纯策略计算约占单核 5%，不含游戏、机器人、序列化和回放开销。

这些数值是预算提案。先测服务器 TPS/MSPT、机器人 CPU、隔离运行时中的平均/P95 决策耗时、RSS 和回放大小，再冻结正式限额。之前 PyTorch 的 CPU 单次结果不能替代 QuickJS 或实际整服压测。

代码异常/超时/总预算用尽，停止该席策略并按公开故障规则判负；平台故障导致整局作废重赛。数据格式错误和当下不可执行的合法动作要分别记录。不能悄悄换成官方机器人，给故障投稿算成绩。

## 7. AGX 接入结构

```text
AGX 投稿/版本/赛程/排行榜
             |
       比赛任务队列
             |
      Minecraft 比赛执行器
       |               |
 隔离 JS 策略进程    Paper + BedWars + 裁判桥接
       |               |
       +-- 合法观察 / 任务 --+
               |
    统一机器人操作 + 真实服务器判定
               |
     比赛结果 / 公共回放 / 私有决策轨迹
```

需要平台仓库中新增：

1. `bedwars` 游戏注册、规则版本、可创建 Agent 枚举、赛季与基线。
2. 对应投稿运行检查：入口、预算、输出 schema、极端观察与故障路径。
3. Minecraft worker 类型、租用/清理竞技场、进程资源限额、失败重试和幂等结果提交。
4. 版本固定的裁判桥接与机器人驱动。赛局复位在同一进程内完成；不是每个决策或每局都重启服务器。
5. 回放协议与网页查看器。记录地图初始块、方块变化、玩家姿态、床/死亡/购买/结算事件；`tick` 对齐。官方回放来自服务器记录，不能把动作在另一进程重跑后假定完全一致。
6. 私有决策轨迹和公开观战信息分离，防止进行中的隐藏状态外流。

当前只读取了公开页面和接口，未对 AGX 写入或发布任何赛项。真正接入前需要拿到该平台的代码与执行器合同；本地试验不需要先改线上服务。

## 8. 本地交付与验收顺序

- 已下载并校验 Paper 1.21 build 130、Screaming BedWars 0.2.44；地图生成插件及配置位于本项目。
- 本地测试命令见 `LOCAL_TRIAL.zh-CN.md`。先验证双队地图、资源生成、商店、放置/挖掘、床与复活、最终淘汰和自动恢复。
- `BedGuard` 是用来凑齐两名参与者、验证规则的守家脚本；不是训练出来的起床战争 AI，也不实现上面的投稿合同。
- 然后实现投稿合同适配器，让两个不同的 `agent.js` 完整比赛；增加超时、无效动作和隐藏信息回归检查。
- 最后才接 AGX worker、网页回放与排行榜。只有真实对局和故障路径都通过后，才可以称为可参赛版本。

Minecraft EULA 必须显式接受。项目 `AGENTS.md` 要求：`Do not silently accept the Minecraft EULA. Provide an explicit script flag or documented manual step.` 准备脚本默认写入 `eula=false`；本次用户已明确同意，随后显式接受并启动本地服务器。

- [rl-minecraft-ai](https://github.com/therohero/rl-minecraft-ai)：仓库描述提供模拟器 PPO 自博弈及真实 Minecraft 桥接；本次仅阅读文档，未复现。

本机 i5-13500HX，Python 3.11.5、PyTorch 2.14.1 CPU、单线程，合成观察各 2,000 次：BC 22,027 参数，平均约 0.035 ms；PPO actor 22,027 参数，总 actor+critic 42,764 参数，平均约 0.147 ms。完整测量见 `runs/local-probe.json`。100 步模拟协议检查通过；它不是 Minecraft 实战，也没有测出服务器 TPS 或胜率。

已进一步把 PPO actor 的数值计算导出成 `submission-kit/model-demo/policy-core.js`：22,027 参数，约 443 KiB，32 组合成输入与 PyTorch 的 logits 最大绝对误差约 1.7×10⁻⁵。使用 QuickJS WASM 隔离运行时测量 500 次，平均约 1.6 ms、P95 约 1.9 ms，详见 `runs/js-policy-probe.json`。这支持“小模型可以打包进 JS”的工程路线；不代表这些特权观察已适合比赛，也不代表该模型已经会玩起床战争。该演示未在 AGX 的真实执行器中运行。

本地起床战争准备程序编译通过。初次 Paper 引导检查在 EULA 处停止；用户随后明确接受，已完成地图生成与基本对局检查，包括购买、复活、拆床、最终淘汰和地图恢复。实时观战页运行在 `127.0.0.1:3007`。这些结果不代表投稿合同或自主学习起床战争策略已实现。
