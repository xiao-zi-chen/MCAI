# 0.7：本地多竞技场与持续补位

一个 Paper 进程现在可以同时运行多个独立的 1v1 起床战争场地。每场的选手、计时、团队升级、缩圈、商店、回放和地图恢复分别维护。比赛中心使用 BullMQ 5.81.5 + ioredis 5.11.1 + 本地 Redis；不用云模型 API。规则仍为 `skyduel-0.6.0`，地图仍为 `sky-harbor-4.0`。

## 运行

先通过 `setup-bedwars.ps1` 安装基本环境，按已有流程接受 Minecraft EULA。停止旧演示，再执行：

```powershell
.\scheduler.ps1 -Mode Prepare -JavaHome 'E:\Java\jdk-21'
.\scheduler.ps1 -Mode Start -RedisExe 'D:\Redis\redis-server.exe'
```

上面的路径为开发机示例，可替换。默认地址是 `http://127.0.0.1:3009/`。首次 Prepare 会备份受控配置、编译两个插件、安装锁定的 npm 依赖，并配置三个世界。原世界、旧回放、模型保留；新场地使用 `bedwars-v6_a2`、`bedwars-v6_a3`。后续启动直接使用 Start，也可以双击根目录的 `打开比赛中心.cmd`。`-NoBrowser` 可抑制自动打开浏览器。

比赛中心的“加入 4 个测试 AI”每次加入四个新账号，每个账号打一场。两套已发布的 22,027 参数权重与 rush/fortify 打法、不同随机种子组合。测试账号数不代表独立训练模型的数量。组织者仍提供规则与运行平台，参赛者最终自行提供策略与训练。

空位恢复后按入队顺序选出两人，同一选手不会同时占两个场地；一场结束时其他比赛继续。暂停和降低并发只停止新的配对，不打断已预留或进行中的比赛。观战按需开启，网页关闭后约三分钟释放闲置观战进程。点击历史结果可看完整 3D 回放，默认仍为平视。

```powershell
.\scheduler.ps1 -Mode Status
.\scheduler.ps1 -Mode Stop
```

Stop 会暂停配对、中止仍在运行的比赛并将其标记为 aborted，再保存世界。Redis 保持运行以保留队列；再次启动后在比赛中心恢复自动开赛。不要同时运行旧的 `showcase-v2.cjs` 自动演示。

## 容量与端口

配置在 `configs/scheduler.local.json`。初始允许同时两场，可在网页升到三场。增加物理场地数量需要同步竞技场配置并在停止服务器后重新 Prepare；`max_active` 只调节已有场地的开局上限。内存可用量低于 512 MB 或平均 MSPT 超过 35 时暂缓新配对，已经进行的比赛继续。

| 服务 | 默认本机端口 |
| --- | --- |
| Minecraft | 25567 |
| 调度控制（持久 TCP） | 25610 |
| 三场独立观察流 | 25600、25601、25602 |
| 专用 Redis | 26379 |
| 比赛中心 | 3009 |
| 按需观战 | 3007、3010、3011 |

控制连接只绑定 localhost，每帧动作不走 HTTP，不按帧落盘。HTTP 用于管理网页；AI 在独立进程运行，不阻塞 BullMQ 锁续期。Java 裁判只在比赛边界写预留凭据和完整回放。正式的跨机部署仍需单独实现认证、网络和隔离。

## 恢复与一致性

- Redis Lua 原子预留两个选手和一个场地，再将确定的比赛 ID 放入 BullMQ。进程若在二者之间退出，下次调度会补写同一项任务。
- 裁判以比赛 ID + 随机令牌校验控制请求。重复 launch 只会获准一次。场地没有“锁超时就直接变空闲”的逻辑。
- 回放使用临时文件、刷盘和替换；成功后才返回 saved。地图必须收到 BedWars 重建完成事件、恢复 WAITING、清空原选手，且两张床的四块方块都恢复。
- 结果按比赛 ID 去重，结果持久化后才释放场地与选手。重试读取现有比赛状态和结果，避免重复发奖或重开已结束的比赛。
- 调度进程重启可以接管仍在运行的 AI 进程；Redis 断线期间不新分配场地，协调租约过期后可以重新取得自己的调度权，并且不会抢占其他活跃调度器。专用 Redis 配置 AOF、`appendfsync always` 与 `noeviction`。
- 重置超时或无法确认状态时隔离该场地，其他场地可以继续。Minecraft 在持有预留时意外重启，会保守隔离该场地，需检查世界和记录后恢复；这部分尚未实现自动地图快照灾难恢复。

Windows 本机测试使用已经安装的 Redis 5.0.14.1，满足所用 BullMQ 的硬性最低版本，但低于其推荐的 6.2。正式部署应使用维护中的 Redis 版本并复测。本实现不启动或修改用户原来的 Redis 服务，另用项目 `runs/scheduler/redis` 数据目录。

## 验证

2026-10-21 在 i5-13500HX / 约 15.7 GiB RAM 的开发机完成首批 **16 个测试账号、8 场自然比赛**。实际使用一个 Minecraft 进程、三个竞技场，峰值六个 AI 同时运行。比赛耗时 73–656 秒；一次只结束并补入自己的场地，其他比赛继续。首批全部完成后，三个场地均确认空闲，16 名选手各计一局，没有重复启动或重复计分。

最终增加释放凭据持久化并部署后，又完成一场 281 秒的自然比赛，验证了保存结果、地图恢复与磁盘释放凭据。后续演示继续使用这套最终部署。

| 实测项目 | 结果 |
| --- | --- |
| 六个 AI 同时运行期间的采样 | 582 次，TPS 约 20 |
| 采样的平均 MSPT | 中位 1.65 ms，最高约 2.73 ms |
| 五秒资源采样中的 Minecraft 工作集 | 约 1559 MiB |
| 六个 AI / 三个控制进程工作集合计 | 约 718 MiB |
| Minecraft、AI、Redis、调度器及两个后台观战进程工作集合计 | 约 2647 MiB；不含操作系统及浏览器渲染 |
| 自动测试 | 76 项通过：调度 10、既有策略/网页 49、空场观战回归 1、规则 16 |
| 调度进程与 Redis 重启 | 原比赛接管、排队与暂停状态恢复；没有盲目重开原比赛 |
| 网页 | 场地选择、平视观战、四名商店村民、完整回放和手机布局通过 |

这些是短时采样，不代表单 tick 的尾延迟或机器容量上限；内存为工作集，不等同于申请内存。八场对局的批次和最终部署追加验证分别记录，不能混算成模型胜率评测。

测试分为真实 Minecraft 对局、调度与恢复测试、网页观战测试；具体机器采样和比赛 ID 见 `docs/verification/v0.7-scheduler.json`。1000 选手测试只创建队列记录，不代表运行了 1000 个 Minecraft AI。资源采样属于本机短时测量，不能据此推算生产容量上限。

```powershell
.\scheduler.ps1 -Mode Redis
node --test local-scheduler/test/scheduler.test.cjs
```

测试使用临时 Redis 命名空间，仅清理自己的键，不清空整个 Redis。新增测试覆盖原子预留、FIFO、晚到选手、结果去重、退出、预留恢复、控制断线、重置失败隔离与错误释放凭据。既有策略/网页测试、规则测试和两个 Java 构建继续通过。

## 范围

这是本机多场运行版本。测试入口仅接受内置模型和策略，尚未接收任意不可信投稿；安全隔离的执行器、AGX 后端、跨机器容量调度、正式排名匹配尚未实现。Agones 的既有示例仍作为后续多机器方案。0.6 离线展示 ZIP 保持原有视频内容，本次新增调度界面从本地服务器观看。
